# 2026-10-15

## Modernisation: starting point

_Drafted by Claude from session discussion; reviewed by author._

**Goal (author):** move OpenDX off autotools and X11/Motif to CMake and a
cross-platform UI, running on Linux, macOS and Windows, and later as a container
and as WebAssembly. This is a multi-session effort, and options and tradeoffs
will be discussed along the way.

**What the code looks like today:**
- Two programs. `dxexec` (`src/exec`, about 820 C files) does the computation;
  `dxui` (`src/uipp`, about 1000 C++ files) is the visual program editor. They
  talk over a socket using DX's script language.
- The exec is mostly portable C. X11 and OpenGL appear only in
  `src/exec/hwrender`, and the software renderer (`Render` module) already runs
  headless.
- The UI is deeply Motif: 284 files include `Xm/`, plus a home-grown framework
  (`uipp/base`) and custom Xt widgets (`uipp/widgets`).
- The OpenGL is fixed-function GL 1.x with GLX (about 82 distinct calls). The
  port layer `hwPortLayer.h` is a usable seam for a new backend.
- The build generates code: `.mdf` module tables, `class.awk` class headers from
  `.X` files, and the `net.y` grammar.
- Not portable as they stand: `fork()` in 13 files, shared-memory arenas in
  `libdx/mem.c`, `rsh`-based distributed execution, and the socket between UI
  and exec.
- Generated build files are committed (`config.status`, `Makefile`s, `libtool`,
  `warnings*`, `tags`). They should go when CMake arrives.

**Proposed phases** (not yet agreed one by one):

| Phase | Work |
|---|---|
| 0 | Build the current autotools tree on Alma9; save `.net` programs and their rendered images as regression references |
| 1 | CMake for the exec side (`libdx`, `dxmods`, `dpexec`); code generators rewritten in Python |
| 2 | Exec embeddable as a library, socket optional (needed for WASM) |
| 3 | New renderer behind `hwPortLayer`, OpenGL 3.3 core / ES 3.0 level |
| 4 | New UI (see ADR 0001) |
| 5 | Container image, then WASM |

## Modernisation: UI toolkit

_Drafted by Claude from session discussion; reviewed by author._

**Qt first, then set aside.** Qt 6 was the first proposal. The author asked
whether it could be avoided, to stay clear of licensing questions: OpenDX is
under the IBM Public License, and a WASM build links Qt (LGPL) statically.

**Would noodles remove the need for Qt?** Only partly. noodles (Meta's node-graph
renderer, studied in the author's Meta-Noodles research) draws the graph canvas
and nothing else. It would replace `WorkspaceW.c`, and fits DX concepts well
(macros as subgraph drill-down, comment decorators as stickers). The rest of the
UI (palette, configuration dialogs, control panels and interactors, image
windows, sequencer, message window, file dialogs) still needs a toolkit.

**Toolkits considered:** Dear ImGui; a browser (HTML/DOM) UI as in
shader-noodles; RmlUi; Nuklear; Slint (reintroduces licensing questions);
wxWidgets and GTK (poor WASM support).

**Browser UI, noted for later.** OpenDX already splits UI and exec over a socket,
so `dxexec` in a container with a browser UI talking the DX protocol over a
WebSocket is a natural fit. It was not chosen now (second language stack, weaker
desktop story), but the protocol boundary is kept so it stays possible.

**What Remex adds** (read 2026-10-15 at `052db54`): its GLFW + GL 3.3 + ImGui app
runs natively, in WebGL2, and from a container on the host display (Wayland
first; Windows 11 through Podman and WSLg). Its `container/` folder (multi-stage
`Containerfile`, `remex_run.py`, `notices.py`, `release.py`) can be reused almost
unchanged. Its web file I/O is parked (Emscripten's in-memory file system loses
files on reload). For OpenDX, which reads and writes real data files, a mounted
work folder in the container is the better route, so the suggested order is
**native → container → WASM**. OpenDX can also offer a headless mode (exec and
software renderer only) for batch rendering.

### Decisions (author, 2026-10-15)

1. **No Qt and no Motif. Dear ImGui + noodles + GLFW**, the same stack as Remex.
   Recorded as [ADR 0001](../adr/0001-ui-toolkit.md).
2. **noodles from the author's fork**, `github.com/nyue/noodles`, branch
   `wasm-port` (`13e27ed`), not upstream.
3. **Set up a diary and ADRs** for this repository, in `docs/diary/` and
   `docs/adr/`. The legacy `doc/` folder is left alone.

### Open questions

- Renderer target: OpenGL 3.3 core / ES 3.0 subset is proposed (ADR 0001 depends
  on it). Qt RHI and WebGPU were considered and are not pursued for now.
- Phase 2: how far to take the in-process exec (threads instead of `fork`, and
  `SharedArrayBuffer` with COOP/COEP headers on the web).
- Distributed execution over `rsh`: drop or replace.
- Dependencies on Windows: vcpkg, Conan or conda-forge (HDF, netCDF, TIFF,
  ImageMagick).
- Next step: phase 0, building the current tree on Alma9 (Motif development
  packages come from EPEL).

## Phase 0: building the old tree on Alma9

_Drafted by Claude from session discussion; reviewed by author._

**Setup.** Installed `motif-devel`, `libXmu-devel`, `libXpm-devel` and `byacc`
with `dnf` (EPEL and CRB are already enabled). Optional format libraries (TIFF,
netCDF, HDF, ImageMagick) are left out, so the baseline is the core build. Builds
run in `~/projects/OpenDX/phase0-autotools/`, outside the repository, because the
autotools output (`config.status`, `Makefile`s, `libtool`) is tracked and an
in-place build changes it.

**What it takes to build with GCC 11.5:**

| Problem | Workaround |
|---|---|
| configure's test program defines `byte`, which clashes with C++17 `std::byte` | `CXXFLAGS=-std=gnu++14` |
| 372 narrowing errors from `*.bm` bitmaps (values above 127 in `char` arrays) | `-Wno-narrowing` |
| `#include <linux/sys.h>` in `libdx/memory.c`; the header is gone and was unused | line deleted (source fix) |
| `return FALSE` from a function returning `char*` (`EditorWindow.C`) | `-fpermissive` |

The committed `configure` (Autoconf 2.59) still works; it was not regenerated.

**HEAD did not run.** `cb93e8f` built, but `dxexec` crashed at startup:

- `c468ee2` ("chipping away at removing warnings", 2016) rewrote `DXGetString`
  (`libdx/string.c`) to call `strlen` on a pointer that is NULL for short strings.
- With that restored, a second crash in `_dxf_ExDictionaryInsert`
  (`dpexec/d.c`), also during startup. Not investigated further.
- The 2016–17 warning-fix commits change about 1,577 source files even with
  whitespace ignored: a mass reformat mixed with casting changes. Not auditable.

**The initial import works.** `8b6f39f` (OpenDX 4.4.4 as first imported) builds
with zero errors under the same workarounds, and a headless script renders
correctly with the software renderer: a computed field, `Isosurface`, `Color`,
`AutoCamera`, `Render`, `WriteImage` gives a shaded orange sphere, 320×240 TIFF.

**Also found:** seven compiled binaries were committed (`dxexec`, `dxui`,
`builder`, `prompter`, `startupui`, `tutor`, `dxlocal`), plus generated sources
and a generic `.gitignore` template that ignores `Makefile`. There are no sample
programs or data in the repository, only stroke fonts.

### Decision (author, 2026-10-15)

**The baseline is `8b6f39f`.** One commit restores every file outside `docs/` to
that commit; history is kept (no force-push) and the 2016–17 work stays in git.
The binaries and generated files the later commits added are removed with it.
Any warning fixes still worth having are redone during the CMake and compiler
work in phase 1.

- Optional format libraries for the baseline: add TIFF, netCDF, HDF and

## Phase 0: reference renders

_Drafted by Claude from session discussion; reviewed by author._

**Decision (author):** our own scripts first (answers the first phase 0 open
question); upstream `dxsamples` to be added before phase 4, when `.net` programs
matter for testing the UI. Scripts and images live in `tests/reference/`,
images as PNG, runner at `tests/run_reference.py`.

**What was built.** Ten headless scripts, one per feature area: isosurface,
colormapped slice, glyphs, streamlines with tubes, axes and caption (fonts),
colour bar, rubber sheet, mesh and boundary lines, importing a native `.dx` file,
and volume rendering. Each makes its own data except the import test, which reads
`tests/reference/data/tetra.dx` through `DXDATA`. The ten PNGs total 292 KB.

**How the runner works.** It calls `dxexec -R -B` directly (not the `dx` shell
launcher, so it can run on Windows later), in a fresh folder per script, and
reads DX's raw `"rgb"` output. Standard library only: PNG is written and read
with `zlib`; its reader was checked against ImageMagick on all ten images, and a
one-pixel change was caught and written out as actual and diff images.

**Things learnt about DX along the way:**
- TIFF output is gamma-corrected (2.0, in `_rw_image.c`); raw RGB is the
  renderer's own pixels, so the references use raw RGB.
- The `"rgb"` format appends frames to an existing file, hence a fresh folder
  per run.
- The software renderer is byte-for-byte repeatable, so comparison is exact for
  now.
- The script language does not allow a module call inside another call's
  arguments.
- Module input order is authoritative in `src/exec/dxmods/dx.mdf`; the bundled
  HTML pages were not useful for looking up call signatures.

### Open questions

- When phase 1 changes the compiler or flags, how much tolerance to allow before
  calling a difference a regression.
- The default colormap is a red-to-blue rainbow. It is DX's own output and
  stays in the references, but any visuals made *for* the author should use a
  Protan-safe palette.

## Phase 1: CMake build of dxexec

_Drafted by Claude from session discussion; reviewed by author._

**Decision (author):** start phase 1 as proposed. The build decisions are
recorded in [ADR 0002](../adr/0002-cmake-build.md).

**Code generators ported to Python** (`tools/codegen/`), each checked byte for
byte against the autotools output: `dx_class.py` (24 class files, `.h` and `.c`,
48 of 48 identical), `zexpand.py` (5 `.Z` templates), `mdf_preprocess.py` and
`mdf2c.py` (`dx.mdf`, `dxcm.mdf`, `user.c`, `usercm.c`). Two finds:
- The Makefile step meant to collapse blank lines in `dx.mdf` never worked: bash's
  `echo` keeps both backslashes in `\\n`, so the `sed` test never matches. The
  port keeps the blank lines, as the real output always had them.
- The MDF preprocessing now feeds the source on stdin, removing a race where both
  rules wrote the same `tmp.c`.

**149 generated or built files removed from git**, all under `src/exec` and
`include/`: 92 objects and libtool files in `libdx`, 48 class files, 5 `.Z`
outputs, `user.c`, `usercm.c`, `dxconfig.h`, `compile.h`. Sources include
generated headers with quotes, so committed copies beside them would have hidden
the CMake output. A copy of the stripped tree was built with autotools: it
regenerated all of them, so that build is unaffected.

**Result.** The CMake `dxexec` builds with no errors (Ninja, 16 s on 16 cores)
and renders all ten references byte for byte. `dxexec` needs `colors.txt`,
`messages`, `dxrc` and `dxfSaveCurrentImage.net` installed in `dx/lib`; without
`colors.txt`, named colours silently fall back to a built-in table and three
references differ.

**Bug found: fixed-size path buffers.** A fresh build installed under a long
path crashed on three references. Cause: `DXROOT` is copied with `sprintf` into
100-byte stack buffers, in `lbmessage.c` (startup; it corrupted the processor
count, "requested 1831821929 processors") and `lbcolor.c` (named colours). This
was in the 4.4.4 code: the autotools build fails the same way from a long path.
Fixed with 1024-byte buffers and `snprintf` bounded by `sizeof`. Found with
AddressSanitizer (`libasan` installed; `dnf history` transaction 159). ASan's
own report crashes under DX's signal handler, so `gdb` with a breakpoint on
`__asan::ReportGenericError` was used to locate it. With the fix, all ten
references pass under ASan with a 206-character `DXROOT`.

**Still to do in phase 1:**
- The same pattern is likely elsewhere: 27 fixed-size buffers named for files,
  paths or roots, and 6 `sprintf("%s/...")` calls in `src/exec`. The reference
  scripts only reach the two fixed so far.
- Turn the compiler workarounds into source fixes (they only affect the UI's
  C++; the exec is C and needed none).
- Warnings: 29 with default flags; none of `-Wall` yet.
- macOS and Windows: make X11/GLX optional so a headless `dxexec` builds.

### Open questions

- Fix the remaining fixed-size buffers now as a sweep, or as found?
- Add a CI job (runners `alma9` and `ubuntu26`) running the
  CMake build and the reference suite?

## Phase 1: fixed-size buffer sweep and _FORTIFY_SOURCE

_Drafted by Claude from session discussion; reviewed by author._

**Scope found.** The built exec code (not the unused `hwrender/gl`, `xgl`,
`starbase`) has 501 unbounded writes into fixed-size char arrays: 216 `sprintf`,
204 `strcpy`, 73 `strcat`, 7 `vsprintf`, 1 `gets`. Far more than the 27 path
buffers first counted.

**How it was swept.** A one-off rewriter (kept outside the repository) changed
`sprintf`/`vsprintf` into `snprintf`/`vsnprintf` with the destination's size,
and `strcpy`/`strcat` into `_dxf_strcpy_n`/`_dxf_strcat_n`, new helpers in
`include/dxbounded.h` that truncate and still return the destination. The size
comes from `DX_ARRAY_SIZE`, which does not compile when given a pointer, so a
wrong guess is a build error rather than a wrong size. Only plain destinations
(variables, members, subscripts) were rewritten; `buf + n` style ones were left.
Result: **385 sites rewritten in 80 files; 104 left as they were** because the
destination is a pointer (the compiler flagged each one).

**Checks.** All ten references byte-identical; all ten pass under ASan with a
206-character `DXROOT`; `WriteImage`/`Import` with a 498-character path work;
the autotools build still compiles the exec.

**Honest finding.** The pre-sweep code (built under ASan in a separate worktree)
also handled the 498-character module paths: those modules already sized their
buffers. Beyond the two `DXROOT` overflows fixed earlier, no test shows a bug
this sweep fixes. Real but unreached hazards exist, e.g. `license.c` builds
`DXROOT` paths into 256-byte and `HOST_LEN` buffers.

### Decision (author, 2026-10-15)

**Keep the full sweep, and add `-D_FORTIFY_SOURCE=2`.** The sweep was offered
with the alternative of about a dozen targeted fixes. Reasons for the full sweep:
the class of bug is gone at every site the compiler can check, there is no
upstream to merge with, and MSVC warns on `sprintf`/`strcpy` everywhere (C4996).
Cost accepted: an over-long string is now cut short silently instead of crashing.

**`_FORTIFY_SOURCE=2`** is set for the exec targets in every optimised build
(not Debug; it needs optimisation). glibc then checks writes into buffers of
known size, including the 104 pointer sites where the caller's buffer is known,
and aborts with a message instead of corrupting memory. Linux/glibc only.

**It found a bug at once:** `libdx/fileio.c` called `open(name, O_WRONLY |
O_CREAT)` with no mode, so created files got whatever permissions were in a
register. Now `0666` (narrowed by the umask), as `_rgb_image.c` already did.

### Open questions

- **Warnings that become errors on newer compilers.** A full build gives 58
  warnings. 29 are `-Wunused-result` added by fortify (unchecked `read`, `write`,
  `fgets` results). The other 29 were already there, and include
  `-Wimplicit-int` (4), `-Wimplicit-function-declaration` (3) and
  `-Wincompatible-pointer-types` (4), which **GCC 14 and newer treat as
  errors**: the build will fail on the `ubuntu26` runner (GCC 15) until they
  are fixed. 17 pointer/int casts are 64-bit hazards worth reading one by one.
- The 104 pointer-destination sites stay unbounded where the caller's buffer
  size is not visible to fortify.

## Phase 1: building with GCC 14

_Drafted by Claude from session discussion; reviewed by author._

**Decision (author):** fix the warnings that newer compilers treat as errors,
before adding CI. GCC 14 was already installed here (`gcc-toolset-14`, 14.2.1),
so the fixes were checked against the real compiler in a second build
(`~/projects/OpenDX/build-gcc14`), not inferred from GCC 11 warnings.

**GCC 14 reported exactly the expected 11 errors, now fixed:**
- `dxmods/_compparse.c`: the parser called `_dxfcclex`, `_dxfccerror` and
  `_dxfcclexerror` without declarations; prototypes added after `YYSTYPE`. The
  grammar `_compparse.y` is not in the repository, so the generated parser is
  effectively the source.
- `dxmods/_grid.c` (3) and `dxmods/streamline.c` (1): K&R parameters with no type
  (implicit `int`); `int` written out, same meaning.
- `dpexec/dpparse.c`, `exobject.c`, `graph.c` (4): tables of delete methods typed
  `int (*)(void *)` initialised with functions taking specific object pointers;
  explicit `(PFIP)` casts. Checked for the future WASM build, where a call
  through a mismatched signature traps: all pointers are i32 there, so the
  signatures match.

**The 17 pointer/integer casts, read one by one:** none was a 64-bit truncation.
- Integers widened into a `Pointer` (graph ids, CRC hash values, object tags) in
  `command.c`, `evalgraph.c`, `d.c`, `hwObjectHash.c`: made explicit through
  `intptr_t`/`uintptr_t` (not `long`, which is 32-bit on Windows).
- `(char) NULL` used to mean `'\0'` (9 places in `command.c`, `dpparse.c`,
  `genimp_io.c`): replaced with `'\0'`.

**One real logic slip, left behaving as before:** `DXCopyModuleId`
(`dpexec/remote.c`) tested `(char *)id == '\0'`, a second NULL test where an
empty-string test was surely meant. Nothing in OpenDX calls it; it is public API
(`include/dx/task.h`) for third-party modules, so the dead test was removed and
the behaviour kept (an empty id is copied), with a comment recording the intent.

**Result.** Both GCC 11 and GCC 14 build with no warnings other than the 29
`-Wunused-result` from `_FORTIFY_SOURCE`, and both render all ten references
**byte for byte**: a newer compiler has not changed a pixel, so the comparison
can stay exact for now.

### Open questions

- `DXCopyModuleId`: change to the intended empty-string behaviour, or keep?
- The 29 unchecked `read`/`write`/`fgets` results: real error handling is a
  separate piece of work.
- GCC 15 (Ubuntu 26.04) is untested here; `gcc-toolset-15` is available from
  the repositories if wanted before CI.
