# 2026-10-15

## Modernisation: starting point

_Drafted by Claude from session discussion; reviewed by author._

**Goal (author):** move OpenDX off autotools and X11/Motif to CMake and a
cross-platform UI, running on Linux, macOS and Windows, and later as a container
and as WebAssembly. This is a multi-session effort, and options and tradeoffs
will be discussed along the way.

**What the code looks like today:**
- Two programs. `dxexec` (`src/exec`, about 820 C files) does the computation;
  `dxui` (`src/uipp`, about 1000 C++ files) is the visual program editor. They
  talk over a socket using DX's script language.
- The exec is mostly portable C. X11 and OpenGL appear only in
  `src/exec/hwrender`, and the software renderer (`Render` module) already runs
  headless.
- The UI is deeply Motif: 284 files include `Xm/`, plus a home-grown framework
  (`uipp/base`) and custom Xt widgets (`uipp/widgets`).
- The OpenGL is fixed-function GL 1.x with GLX (about 82 distinct calls). The
  port layer `hwPortLayer.h` is a usable seam for a new backend.
- The build generates code: `.mdf` module tables, `class.awk` class headers from
  `.X` files, and the `net.y` grammar.
- Not portable as they stand: `fork()` in 13 files, shared-memory arenas in
  `libdx/mem.c`, `rsh`-based distributed execution, and the socket between UI
  and exec.
- Generated build files are committed (`config.status`, `Makefile`s, `libtool`,
  `warnings*`, `tags`). They should go when CMake arrives.

**Proposed phases** (not yet agreed one by one):

| Phase | Work |
|---|---|
| 0 | Build the current autotools tree on Alma9; save `.net` programs and their rendered images as regression references |
| 1 | CMake for the exec side (`libdx`, `dxmods`, `dpexec`); code generators rewritten in Python |
| 2 | Exec embeddable as a library, socket optional (needed for WASM) |
| 3 | New renderer behind `hwPortLayer`, OpenGL 3.3 core / ES 3.0 level |
| 4 | New UI (see ADR 0001) |
| 5 | Container image, then WASM |

## Modernisation: UI toolkit

_Drafted by Claude from session discussion; reviewed by author._

**Qt first, then set aside.** Qt 6 was the first proposal. The author asked
whether it could be avoided, to stay clear of licensing questions: OpenDX is
under the IBM Public License, and a WASM build links Qt (LGPL) statically.

**Would noodles remove the need for Qt?** Only partly. noodles (Meta's node-graph
renderer, studied in the author's Meta-Noodles research) draws the graph canvas
and nothing else. It would replace `WorkspaceW.c`, and fits DX concepts well
(macros as subgraph drill-down, comment decorators as stickers). The rest of the
UI (palette, configuration dialogs, control panels and interactors, image
windows, sequencer, message window, file dialogs) still needs a toolkit.

**Toolkits considered:** Dear ImGui; a browser (HTML/DOM) UI as in
shader-noodles; RmlUi; Nuklear; Slint (reintroduces licensing questions);
wxWidgets and GTK (poor WASM support).

**Browser UI, noted for later.** OpenDX already splits UI and exec over a socket,
so `dxexec` in a container with a browser UI talking the DX protocol over a
WebSocket is a natural fit. It was not chosen now (second language stack, weaker
desktop story), but the protocol boundary is kept so it stays possible.

**What Remex adds** (read 2026-10-15 at `052db54`): its GLFW + GL 3.3 + ImGui app
runs natively, in WebGL2, and from a container on the host display (Wayland
first; Windows 11 through Podman and WSLg). Its `container/` folder (multi-stage
`Containerfile`, `remex_run.py`, `notices.py`, `release.py`) can be reused almost
unchanged. Its web file I/O is parked (Emscripten's in-memory file system loses
files on reload). For OpenDX, which reads and writes real data files, a mounted
work folder in the container is the better route, so the suggested order is
**native → container → WASM**. OpenDX can also offer a headless mode (exec and
software renderer only) for batch rendering.

### Decisions (author, 2026-10-15)

1. **No Qt and no Motif. Dear ImGui + noodles + GLFW**, the same stack as Remex.
   Recorded as [ADR 0001](../adr/0001-ui-toolkit.md).
2. **noodles from the author's fork**, `github.com/nyue/noodles`, branch
   `wasm-port` (`13e27ed`), not upstream.
3. **Set up a diary and ADRs** for this repository, in `docs/diary/` and
   `docs/adr/`. The legacy `doc/` folder is left alone.

### Open questions

- Renderer target: OpenGL 3.3 core / ES 3.0 subset is proposed (ADR 0001 depends
  on it). Qt RHI and WebGPU were considered and are not pursued for now.
- Phase 2: how far to take the in-process exec (threads instead of `fork`, and
  `SharedArrayBuffer` with COOP/COEP headers on the web).
- Distributed execution over `rsh`: drop or replace.
- Dependencies on Windows: vcpkg, Conan or conda-forge (HDF, netCDF, TIFF,
  ImageMagick).
- Next step: phase 0, building the current tree on Alma9 (Motif development
  packages come from EPEL).

## Phase 0: building the old tree on Alma9

_Drafted by Claude from session discussion; reviewed by author._

**Setup.** Installed `motif-devel`, `libXmu-devel`, `libXpm-devel` and `byacc`
with `dnf` (EPEL and CRB are already enabled). Optional format libraries (TIFF,
netCDF, HDF, ImageMagick) are left out, so the baseline is the core build. Builds
run in `~/projects/OpenDX/phase0-autotools/`, outside the repository, because the
autotools output (`config.status`, `Makefile`s, `libtool`) is tracked and an
in-place build changes it.

**What it takes to build with GCC 11.5:**

| Problem | Workaround |
|---|---|
| configure's test program defines `byte`, which clashes with C++17 `std::byte` | `CXXFLAGS=-std=gnu++14` |
| 372 narrowing errors from `*.bm` bitmaps (values above 127 in `char` arrays) | `-Wno-narrowing` |
| `#include <linux/sys.h>` in `libdx/memory.c`; the header is gone and was unused | line deleted (source fix) |
| `return FALSE` from a function returning `char*` (`EditorWindow.C`) | `-fpermissive` |

The committed `configure` (Autoconf 2.59) still works; it was not regenerated.

**HEAD did not run.** `cb93e8f` built, but `dxexec` crashed at startup:

- `c468ee2` ("chipping away at removing warnings", 2016) rewrote `DXGetString`
  (`libdx/string.c`) to call `strlen` on a pointer that is NULL for short strings.
- With that restored, a second crash in `_dxf_ExDictionaryInsert`
  (`dpexec/d.c`), also during startup. Not investigated further.
- The 2016–17 warning-fix commits change about 1,577 source files even with
  whitespace ignored: a mass reformat mixed with casting changes. Not auditable.

**The initial import works.** `8b6f39f` (OpenDX 4.4.4 as first imported) builds
with zero errors under the same workarounds, and a headless script renders
correctly with the software renderer: a computed field, `Isosurface`, `Color`,
`AutoCamera`, `Render`, `WriteImage` gives a shaded orange sphere, 320×240 TIFF.

**Also found:** seven compiled binaries were committed (`dxexec`, `dxui`,
`builder`, `prompter`, `startupui`, `tutor`, `dxlocal`), plus generated sources
and a generic `.gitignore` template that ignores `Makefile`. There are no sample
programs or data in the repository, only stroke fonts.

### Decision (author, 2026-10-15)

**The baseline is `8b6f39f`.** One commit restores every file outside `docs/` to
that commit; history is kept (no force-push) and the 2016–17 work stays in git.
The binaries and generated files the later commits added are removed with it.
Any warning fixes still worth having are redone during the CMake and compiler
work in phase 1.

### Open questions

- Reference programs and data: there is no `dxsamples` in the repository. Write
  our own scripts, fetch the upstream samples, or both?
- Optional format libraries for the baseline: add TIFF, netCDF, HDF and
  ImageMagick now, or in phase 1?
- Should the compiler workarounds become source fixes now, or wait for phase 1?
