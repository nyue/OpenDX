# 2026-10-16

## UI: slice 2, images in the Image panel

_Drafted by Claude from session discussion; reviewed by author._

**Decision (author):** start slice 2: show rendered images inside the UI instead
of the executive's own X windows.

**How images reach the UI.** In exec-only mode an Image node is not a module:
each `.net` file carries a generated `macro Image(...)` that works out the camera
and axes and ends in `Display()` calls, which open X windows. The UI now sends a
rewritten copy of the file (`src/ui/exec/NetScript.cpp`):
- Inside `macro Image(...)`, `Display(` becomes `DxuiShow(id, ` (result unused)
  or `DxuiDisplay(id, ` (result assigned), keeping each file's own camera and
  axes logic whatever DX version wrote it.
- A Display node in the network gets the same treatment, with `"Display_N"` as
  the id.
- `DxuiShow`/`DxuiDisplay` are DX script macros sent first: render when given a
  camera, then `WriteImage(image, <dir>/<id>, "rgb", 0)` (frame 0 overwrites;
  plain "rgb" appends). They take Display's 4 or 8 inputs.
- `ImagePanel` watches a per-process folder (`$TMPDIR/dxui2-images-<pid>`) four
  times a second and shows one tab per image, fitted to the panel, with DX's
  display gamma (`DXGAMMA`, else 2.0 on Linux, as `libdx/displayx.c` uses).

Alternatives not chosen for now: the exec sending pixels over the DXLink
connection (needs exec changes), or drawing in the UI's own GL context (waits for
the new renderer, phase 3).

**Result.** No X display is needed for images: the sweep ran with `DISPLAY`
pointing at a display that does not exist. Over the 122 sample programs with
Image nodes, **118 run without errors and produce images** (150 images from 139
Image nodes plus Display nodes). The other four are sample-setup or legacy
issues: an external filter at an old path (`ImportExternalFilter`), a font path
that only resolves in the old install layout (`SpecialCharacters`), the
interactive `SuperviseWindow` module (`InsetImage`), and an `Inquire` data error
inside a sample macro (`SalesOnStates`, not looked at).

**Exec bug fixed:** when an X display could not be opened, `delete_window`
(`libdx/displayx.c`) unregistered an input handler for a NULL display and the
executive crashed. Now it reports `Cannot open X display` and carries on. Found
through `UsingEqualize`, which uses a Display node next to its Image node. The
reference images are unchanged.

**Process lifecycle**, each tested:
- `SIGINT`/`SIGTERM` quit the UI cleanly (stops dxexec, removes the folder).
- **dxexec does not exit when the UI disconnects.** Two orphans from early smoke
  tests were found and stopped. On Linux the UI now starts dxexec with
  `fork`+`exec` and `PR_SET_PDEATHSIG`, so a `kill -9` of the UI also stops it.
- A folder left by a killed UI is removed at the next start, only when its
  process no longer exists.

**Macros and data.** `DXMACROS` (where `include` finds macros) is now a setting
(`--macros`, default from the environment); 14 samples need the samples'
`macros/` folder. DXDATA and DXMACROS are inherited unless given, after a
regression where setting one explicitly dropped the inherited value.

**Tools:** `exec_check --images DIR` runs a file as the UI does;
`--print-script` prints the rewritten script.

### Open questions

- Interaction with images (rotate, zoom, pick) needs the exec to re-render on
  camera changes: a next slice, or wait for the new renderer?
- `SalesOnStates`: is the `Inquire` error a DX bug or the sample?
- Still open from 2026-10-15: the program's name, ADR 0003 for the exec link,
  graph orientation.

## UI: slice 3, moving nodes and saving

_Drafted by Claude from session discussion; reviewed by author._

**Context.** The author found the graph's nodes could not be moved. That was by
design (slice 1 was view-only), and not part of the image-interaction work
planned next, which is about rotating and zooming in the Image panel. Graph
editing was laid out in steps: (1) move nodes, (2) save, (3) real editing
(wires, adding nodes, input values), which needs `dx.mdf` and a full writer.

**Decision (author):** do steps 1 and 2 now.

**What was built:**
- **Dragging** (`GraphView`): a press on a node selects it and drags it once the
  pointer has moved 4 pixels; a press on empty space still pans. The end of a
  drag is converted back to DX workspace pixels through the view's transpose,
  scales and page-cell offset (now kept per node), rounded and snapped there,
  and reported as a `NodeMove`. A page backdrop grows to keep a node inside.
- **Undo and redo** of moves (Edit menu, Ctrl+Z, Ctrl+Shift+Z or Ctrl+Y).
  Undoing back to the saved state clears the unsaved marker.
- **Saving** (`src/ui/net/NetWriter.cpp`): only the `x = X, y = Y` numbers on
  each node's `// node Module[inst]:` line change; every other byte of the file
  is kept, so DX and the legacy UI still read it. If a node's comment is not on
  the line the parser recorded, nothing is written. Files are written beside the
  original and renamed over it, keeping its permissions. File menu: Save
  (Ctrl+S) and Save As.
- **Unsaved changes**: `*` in the window title; a Save / Discard / Cancel prompt
  before closing the window, Quit, or opening another file.
- Warnings: the new UI code now builds with `-Wall -Wextra`, with no warnings.

**Checks:**
- `net_check --roundtrip` on all 262 samples: unchanged positions give the file
  back byte for byte; with every node moved, the file re-parses with the new
  positions and only node comment lines differ.
- On a copy of `Gradient.net`, driven with real mouse events: dragging Import
  marked the file changed; Ctrl+S saved a file differing only in Import's line
  (`x = 97, y = 57` became `x = 188, y = 152`), which still parses and runs in
  dxexec; Ctrl+Z then Ctrl+S gave back the original byte for byte. The prompt's
  Cancel, Discard and Save paths each did the right thing. The sample in
  `dxsamples` was never touched.

### Open questions

- Next: real editing (wires, add/delete nodes, input values, needs `dx.mdf`), or
  interaction in the Image panel?
- Grid snapping for moves (the legacy UI had a `layout: snap` setting in the
  file header)?

## UI: slice 4, full graph editing with module definitions

_Drafted by Claude from session discussion; reviewed by author._

**Decision (author):** full graph editing next, using `dx.mdf`.

**Built in three steps:**

1. **Module definitions** (`src/ui/net/ModuleDefs.cpp`). Read from the exec's
   `dx.mdf` (161 modules), the legacy UI's `ui.mdf` (14: Image, Transmitter,
   Input/Output, ...; now installed to `dx/ui/ui.mdf` as the legacy build does),
   `--mdf` files, and macros found in `DXMACROS` folders and the opened file's
   own folder (as the legacy UI did). Inputs carry name, types, default,
   description, menu options and `visible` (1 shown, 0 hidden until exposed, 2
   internal); `REPEAT n` repeats the last n inputs (Collect). Some modules take
   more outputs than they declare (Route, Switch): the file's count wins.
   `net_check --coverage`: with all sample macro folders, 36 of 6,345 sample
   nodes have no definition (34 are JavaDX's `WebOptions`, defined nowhere).
   In the UI, pins have real names, inputs show as DX shows them (the file's
   `visible`, else the definition's), and Details lists each input with its
   wire, value or default.
2. **Editing** (`src/ui/net/NetEdit.cpp`, UI in `GraphView` and `main.cpp`):
   drag output to input to connect (one wire per input: replaces), drag a wired
   input to empty space or the Details "x" to disconnect, a Modules palette
   (categories, filter; double-click or drag onto the graph) to add, Delete to
   remove, Details fields to set input values (DX syntax; empty = default). Loops
   are refused, including through Transmitter/Receiver pairs; a Transmitter
   still feeding Receivers cannot be deleted. Undo/redo keep the network before
   and after each edit.
3. **Saving structural edits** (`writeNet` in `src/ui/net/NetWriter.cpp`,
   written by a sub-agent): node blocks are kept byte for byte when untouched,
   regenerated in the legacy UI's format (`Node.C` netPrintCommentHeader /
   netNodeString) when changed, re-ordered only as wiring requires; value
   assignments likewise. A new Image node gets its id, CacheScene line and a
   `macro Image` wrapper (`NetImageMacro.cpp`, the legacy `ImageNode::printMacro`
   text). Every save writes from the file as loaded to the current model. The UI
   tries the writer after each structural edit and takes back, with the reason,
   any edit it could not save, so the program is always savable. **Refused**:
   adding interactors and other UI-state nodes (Scalar, Selector, Colormap,
   Sequencer, ...), changing their wires or values, adding Transmitter/Receiver
   (no label editing yet), adding/deleting macro Input/Output.

**Checks:**
- Identity: all 262 samples written back unchanged are byte-identical.
- Random edit sequences (`net_check --edit-roundtrip`), re-parsed and compared
  with the edited model: the agent ran seeds 1-5 (13,100 sequences, ~121k edits);
  re-checked here with seeds 1, 7 and 11 after the NetEdit fixes: 1,310/1,310
  each.
- DX acceptance (agent): 2 x 262 edited files through dxexec; no new syntax
  errors, argument-count warnings or undefined variables. Behaviour-preserving
  edits give the same executive messages as the original in 256/262 files (the
  other 6 are artefacts of the test's own edits).
- End to end in the GUI on a copy of Gradient.net: add Isosurface from the
  palette, wire MapToPlane into it and it into Collect, Ctrl+S: the saved file
  differs only by the new block, Collect's argument and the new NULL
  assignments; it runs, and the picture shows the contour line instead of the
  coloured plane.

**Unresolved: one lost Ctrl+S.** In about 15 scripted GUI runs, twice the app
never saw Ctrl+S (no save, no message; Ctrl+E a second later worked). Eight
runs with key logging all received the key and saved. Likely the synthetic
input (xdotool on Xvfb without a window manager), but not proven.

### Open questions

- Interactors (Scalar, Selector, ...) and Transmitter/Receiver labels: the next
  editing step, or later?
- A node's pins only show its visible inputs; wiring into a hidden input needs
  a way to expose inputs (the legacy UI's "Expand").
- Type checking of wires (types are in `dx.mdf`); today DX reports mismatches
  when the program runs.

**Question from the author: no 3D interaction in the Image panel?** Expected:

X window with its OpenGL renderer, which slice 2 replaced. Interaction can come
back either as a stepped version now (mouse changes the Image node's camera
inputs, the executive re-renders) or smoothly with the new renderer (phase 3)
drawing in the UI's own GL context.

**Decision (author):** next, exposing hidden inputs, so they can be wired.

**What was built:**
- `NetEdit::setInputVisible`: shows or hides an input, written as
  `// input[i]: visible = 0|1`. A wired input cannot be hidden; an internal
  input (`visible:2`) cannot be shown.
- `NetEdit::inputShown`: the one rule for whether an input appears on its node
  (wired; else the file's `visible`; else the definition's; with no definition,
  every input of a node with at most 10). The graph view and Details both use
  it, so they cannot disagree.
- Details: a checkbox per input (wired inputs ticked and locked), and **Show
  all** / **Hide unused** buttons (the legacy Expand/Collapse), each one
  undoable edit.

**Checks:**
- The structural writer already handled visibility. Show/hide was added to the
  random edits of `net_check --edit-roundtrip`: seeds 1, 7, 11 and 23 pass
  1,310/1,310 each; one seed alone made 164 show/hide edits.
- In the GUI on a copy of Gradient.net: AutoGlyph's Show all, then hiding
  `ratio`, saved exactly three new lines in its block (`input[5]: visible = 0`,
  `input[6]` and `input[7]: visible = 1`); a newly shown pin (`min`) took a
  wire.

## UI: slice 5, stepped 3D interaction in the Image panel

_Drafted by Claude from session discussion; reviewed by author._

**Decision (author):** the stepped version now (the smooth one waits for the new
renderer, phase 3).

**How it works:**
- **Starting camera from the executive.** The UI's rewrite (`NetScript.cpp`) adds
  `DxuiCamera(id, camera);` at the end of each `macro Image` wrapper (`camera` is
  one of that macro's outputs in every DX version's wrapper). `DxuiCamera`
  reads the camera with `Inquire` (`camera to/from/up/perspective`, and `camera
  width` or `camera angle` chosen by `Switch`, which evaluates only the input it
  selects) and sends each with `DXLOutput`, labelled `dxuicam:<id>:<what>`. They
  arrive as `PACK_LINK` packets; `ExecClient` now listens for those and gives
  them a `Value` kind. This works for automatic cameras (`useVector = 0`) too.
- **Mouse.** In the Image panel: left drag orbits the eye around the look-to
  point (`Camera.h`), middle/right drag pans, the wheel zooms (orthographic:
  `width`; perspective: the eye moves in).
- **Stepped re-render.** While moving, at most four times a second, the UI sends
  the Image node's camera inputs (`main_Image_2_in_4 = 1; ..._in_5 = to; ...`)
  and `main();`. DX's cache means only the parts whose inputs changed run again.
- **Kept with the program.** When a drag ends (or the wheel rests for 0.6 s) the
  camera goes into the Image node's inputs as one undoable edit, so it is saved.

**Checks** (Xvfb, real mouse events):
- Gradient.net (orthographic, explicit camera): a drag tilted the plane into 3D,
  the wheel zoomed; the saved file changed only the Image node's `from`,
  `width` and `up` (comment lines and assignments), with no executive errors.
- CappedIso.net (perspective): rotate and zoom both work.
- The image sweep is unchanged: 118 of 122 programs with Image nodes render.

**Limitation found:** every step re-runs `main()`, so modules that keep state
advance with it. GetSet.net accumulates a total on each run, and its total rose
2 -> 12 during one drag. The legacy UI re-rendered inside the image window
without re-running the network; that comes back with the new renderer.

### Open questions

- Only Image nodes are interactive; Display nodes have no camera inputs.
- No "reset view" yet (the legacy UI had one).

## Update: why the 3D interaction was slow

_Drafted by Claude from session discussion; reviewed by author._

The author found the interaction very slow on a workstation with an NVIDIA GPU.
The GPU only draws the UI: pictures come from the executive's software
renderer. Claude's first explanation blamed that renderer; **measuring showed it
was wrong**: in dxexec alone, Gradient's whole first run takes 0.03 s and a
camera step 5-8 ms at 640x480 (CappedIso the same). The delay was the UI's own
pipeline: at most one camera every 0.25 s, the image folder looked at every
0.25 s, and the UI loop waking every 0.1 s when idle, about half a second per
step.

**Fixed:** one re-render in flight at a time, the next camera sent as soon as
the previous image arrives (given up after a second); while waiting, the image
file is checked every frame and the loop waits 2 ms instead of 100 ms.
`DXUI_TIMING=1` prints each step's latency to stderr. Measured on CappedIso with
a 2-second drag of 60 mouse moves: 60 re-renders, camera-to-image 11-31 ms
(median 14 ms), none given up; the final image is intact.

Still true: every step re-runs `main()` (the GetSet limitation above), and much
heavier programs will be as slow as their software render. The GPU will matter
once the new renderer (phase 3) draws scenes in the UI's own GL context.
